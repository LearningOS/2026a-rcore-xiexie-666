# 实验五报告：死锁检测（ch8）

## 一、功能实现总结（200 字以内）

在 `ProcessControlBlockInner` 里加一个 `DeadlockDetector`，为互斥锁和信号量各维护一套银行家算法所需的 `allocation` / `pending` 矩阵（行是 tid、列是资源 id，按需扩容）。`sys_mutex_lock`、`sys_semaphore_down` 先算出各资源的可用量（`Mutex` 特性与 `Semaphore` 各加一个 `available()`），**只在这次请求真的会阻塞时**才跑安全性检查：不安全就直接返回 `-0xDEAD`，安全则记下 pending 再阻塞。`unlock`/`up` 归还资源。安全性检查里线程的 Need 取法很关键：当前请求线程用本次请求，其余线程**只有处于 `Blocked` 状态才计入它的 pending**，这样既能在 sem1 里查出死锁，又不会把 sem2 里已经唤醒但尚未恢复执行的线程误算成等待者。此外按题面要求补上了上一章的 `sys_get_time`。

## 三、问答作业

### 1. 主线程（0 号线程）退出时视为整个进程退出，需要回收哪些资源？其他线程的 TCB 可能在哪些位置被引用、是否需回收，为什么？

**主线程退出时要做的事**（对应 `exit_current_and_run_next` 里 `tid == 0` 的分支）：

1. 把进程从 `pid2process` 映射表里摘掉，置 `is_zombie = true` 并记录 `exit_code`，供父进程 `waittid` 取用；
2. 把该进程的所有子进程重新挂到 INITPROC 名下，避免它们变成孤儿；
3. 遍历该进程的 `tasks`，对每个线程做 `remove_inactive_task`：从进程的线程表移除、从 PROCESSOR 的定时器队列移除，并归还 `TaskUserRes`（tid、`trap_cx` 所在物理页、用户栈）；
4. `memory_set.recycle_data_pages()` 释放整个用户地址空间的物理页；
5. `fd_table.clear()` 关闭所有打开的文件（`Arc` 归零会触发 pipe 等资源的 drop）；
6. `children.clear()`、`tasks.clear()`。

另外还要注意**内核栈不能立刻释放**：当前这个正在退出的线程正在使用它自己的内核栈，所以代码里 `tid != 0` 时只 `drop(task)`，真正的回收靠 TCB 的 `Drop`；而 `tid == 0` 时把 task 挂进 PROCESSOR 的 stopping 列表，等调度切回 idle 之后再回收，否则会踩到自己还踩着的栈。

**其他线程的 TCB 可能被引用的位置**：

- 进程的 `tasks: Vec<Option<Arc<TaskControlBlock>>>`（最主要的强引用）；
- `PROCESSOR.current`（正在运行的那个线程）；
- 各类等待队列：`MutexBlockingInner.wait_queue`、`SemaphoreInner.wait_queue`、`CondvarInner.wait_queue` 里都存着 `Arc<TaskControlBlock>`；
- `TaskControlBlock.process` 是 `Weak<ProcessControlBlock>`（弱引用，不阻止回收），但 PCB 的 `children` 反过来持有子进程 PCB 的 `Arc`；
- `waittid` 只记 tid 这个数字，不是 `Arc`，不构成引用。

**是否要回收：必须回收。** 三个理由：

- **泄漏**：`Arc` 计数不归零，TCB 的 `Drop` 就不会跑，它持有的内核栈区间就永远留在 KERNEL_SPACE 里，`KernelStack` 的 `Drop` 也无法 `remove_area_with_start_vpn`。线程多了之后内核空间被耗尽，新线程再也建不起来。
- **错误唤醒**：如果某个 `Blocked` 线程的 TCB 还挂在某个信号量/锁的 `wait_queue` 里而没被清掉，之后别人 `up`/`unlock` 时会 `wakeup_task` 一个"已经退出"的线程，把它置成 `Ready` 重新调度，可它的用户地址空间已经回收、`res` 已经是 None，一执行就非法访存或 panic。
- **资源与语义**：tid 不归还，后续 `thread_create` 会因为 tid 耗尽失败；父进程的 `waittid` 也永远等不到结果。

所以回收的关键不只是"释放内存"，而是**先把所有等待队列、定时器队列、进程线程表里的那几处强引用摘干净**，让计数自然归零。

### 2. Mutex1（`while` 循环重试）与 Mutex2（只 `if` 一次）的区别，以及可能的问题

```c
// Mutex1
void lock() {
    while (locked) { /* 让出 CPU / 阻塞等待，然后回到循环顶部 */ }
    locked = true;
}
// Mutex2
void lock() {
    if (locked) { /* 阻塞一次，被唤醒后不再检查 */ }
    locked = true;   // 或直接返回
}
```

**区别只在"被唤醒之后是否重新检查条件"**：Mutex1 用 `while` 把"检查—等待"包成循环，每次醒来都重新判断锁是否真的空闲；Mutex2 用 `if`，只判断一次，被唤醒后无条件往下走，认为锁已经归自己了。

**Mutex2 的问题**：

- **虚假唤醒 / 唤醒丢失下抢跑进临界区**。阻塞式锁的 `unlock` 常见实现是"若等待队列非空，就把队首线程唤醒并**保持 `locked = 1`，把锁直接移交**"。移交只保证"排在队首的那个线程将获得锁"，不保证它在恢复执行时锁一定还是它的：从 `wakeup_task` 到它真正被调度上 CPU，中间可能过了若干个时间片，如果此时又有第三种路径（例如同一把锁被另一个新来的线程 `Mutex2::lock` 时看到的 `locked` 恰好为 0，或者别处把锁 concat/复用）拿到锁，被唤醒者一恢复就认为自己在临界区里，于是**两个线程同时进入临界区**，互斥被破坏，共享数据出现数据竞争。
- **条件已不成立仍继续执行**。这是条件变量的经典教训：`wait` 返回只代表"可能有人动了状态"，不代表"我要的条件成立"。用 `if` 包 `wait`、醒来不重新检查，就会在条件其实不满足时继续往下跑。这里的状态就是 `locked`，同理。
- **一次唤醒对应一次检查**的假设不成立：多个线程被唤醒、或唤醒信号在真正等待前就到达，都会让 `if` 版本的判断落在过时的信息上。

**Mutex1 是对的**，因为循环保证"退出循环"与"成功置 `locked = true`"之间条件没有重新变坏。它的代价是：如果实现成忙等（`MutexSpin` 那样反复 `suspend` 重试），在临界区较长或竞争激烈时会浪费 CPU、并加剧优先级反转；但正确性不受影响。所以结论是 **等锁一定要用 `while` 而不是 `if`**。

## 五、对本次实验的看法（可选）

- 这一章真正的难点不在写代码，而在**"银行家算法里的 Available / Allocation / Need 在真实内核里到底对应什么"**。课上的模型天然假设"资源申请是显式排队、可一次性全部满足"，而这里的 `down` 是会真的阻塞的：一个线程请求资源失败后就睡在等待队列里，它的"待满足请求"只能由我们自己记下来。我先试了"Need 只记当前这一次请求"，结果 sem1 的每次请求都被判安全、根本查不出死锁；又试了"所有还没被满足的 pending 都算进 Need"，结果 sem2 被误判成死锁（屏障信号量上已经被 `up` 唤醒、但还没恢复执行的线程把 `Available` 算成了 0）。最后定下来的规则是：**只把处于 `Blocked` 状态的线程的 pending 计入 Need**，这样"已被唤醒 = 实际上已经拿到资源"就自然成立了。规则只有一句，但它决定了两边的正确答案。
- 另一个体会是"**检测点要贴着阻塞点**"：只有 `available == 0`、也就是这次请求真的会让人睡下去的时候才值得做安全性检查，否则会把大量本来能直接成功的请求也判成死锁。同理，`allocation` 必须等到 `lock()`/`down()` 真正返回之后才记，不能在检查时提前记。
- 一个值得记下的坑：整套测例第一次跑只过 23/25，两个 semaphore 测例直接卡死、连自己线程的打印都没有。查下来**和死锁检测毫无关系**——ch8 模板里的 `sys_get_time` 是未实现的桩，返回 -1，而测例主线程在放行子线程前要 `sleep(500)`，`sleep` 依赖 `get_time()`，拿回 -1 就变成永远等不满足的条件，于是主线程死在放行那一步。把上一章的 `sys_get_time` 按页表逐段拷回补上之后，一次就全过了。教训是：**排查"卡住"要先确认"卡在哪"，别默认是自己新写的那部分代码**，日志里那句 `sys_get_time NOT IMPLEMENTED` 一直都在。
